# ShadowLemon V0.2 过墙能力评估与解决方案

> 依据：GFW Report 的两篇论文
> - *How the Great Firewall of China Detects and Blocks Fully Encrypted Traffic*（USENIX Security 2023）：GFW 自 2021-11 起对"全加密流量"进行**纯被动实时封锁**。
> - *CircumVolve: Automated Discovery of Censorship Evasion Strategies Using LLMs*（CCS 2026）：用 LLM 自动发现针对 DNS/HTTP/TLS/QUIC/TCP 的审查规避策略，共 47 种，核心是利用 **DPI 与实际端点之间的解析差异**。

## 1. 结论（先看这一节）

> **架构已变更**：外部传输现在是 **UDP-only**。TCP 端口绑定在配置校验阶段被拒绝，SOCKS5 CONNECT（TCP 目标）走 UDP 隧道的可靠层。USENIX'23 的 GFW 全加密检测器只检查客户端发出的**第一个 TCP 数据包**（§4.4–4.5），因此**对当前 ShadowLemon 流量不再适用**。下文所有 TCP 实测数据都是改造前的历史基线，保留作对照，不代表当前暴露面。

| 传输 | 能否过墙 | 依据 |
|---|---|---|
| **TCP（历史，已移除）** | 历史基线：大概率不能（在 GFW 监控的 IP 范围内） | 首个 TCP 数据包是均匀随机的，命中 GFW"全加密流量"封锁条件；实测 60/60 首包全部不满足任何豁免规则。当前版本不再有 TCP 外部传输，该系统不适用于现有流量 |
| **UDP（当前唯一外部传输）** | **不受 USENIX'23 该系统影响** | 论文 §4.4 明确：该被动系统只针对 TCP；即使三元组因 TCP 被封，发往同一 (IP, port) 的 UDP 不受影响。但 QDPI 的 `entropy_score` 高熵分析仍然成立，详见 `traffic-analysis.md` |
| 主动探测 | **当前防护较好** | 对畸形/认证失败报文零响应字节，符合 probe-resistance 要求 |

**必须纠正我之前的一条建议**：换非知名端口只能消除 nDPI 的 `TPLINK_SHP` **误报**，**对 GFW 无效**——论文 §4.4 明确"所有端口都可能被阻断，在不寻常端口上运行翻墙服务器并不能缓解封锁"。GFW 更依赖**目标 IP 范围**（论文 §6：只监控热门数据中心 IP 的约 26% 连接），所以选 IP 比选端口重要得多。

## 2. GFW 的检测算法（论文算法 1，历史 TCP-only 系统）

GFW 不直接定义"什么是全加密流量"，而是对**客户端发送的第一个 TCP 载荷**应用至少 5 条**豁免规则**；只要命中任意一条就放行，否则阻断。**这套算法从不检查 UDP；当前 UDP-only 的 ShadowLemon 不在其判定路径内。** 记录于此是为了完整复现历史实测，并为未来可能的 UDP 侧检测提供参考。

| 规则 | 豁免条件 |
|---|---|
| Ex1 | `popcount(pkt)/len(pkt) ≤ 3.4` 或 `≥ 4.6`（粗略熵检测；均匀随机数据 ≈4.0 → **不豁免 → 阻断**） |
| Ex2 | 前 6 个及以上字节全为可打印 ASCII `[0x20,0x7e]` |
| Ex3 | 超过 50% 字节为可打印 ASCII |
| Ex4 | 存在超过 20 个连续可打印 ASCII 字节 |
| Ex5 | 前几个字节匹配 TLS（`[\x16-\x17]\x03[\x00-\x09]`）或 HTTP 方法 + 空格 |

关键行为：
- **只检查第一个 TCP 数据包**，不做多包重组（§4.5）；
- 只检查 **客户端 → 服务器**方向；
- 触发后对同一三元组残留封锁 120–180 秒；
- 阻断是**概率性的**（约 26%），且只针对热门数据中心 IP 段。

## 3. 实测：ShadowLemon 的首包命中哪条规则（历史 TCP 外部传输）

用改造前的 pcap，对每条连接的**第一个客户端 TCP 载荷**按算法 1 逐条判定（`python3 /tmp/opencode/gfw_check.py`）。这些首包来自已移除的 TCP 外部传输，不代表当前 UDP-only 版本的线上特征：

| 版本 | 首包数 | Ex1 | Ex2 | Ex3 | Ex4 | Ex5 | 判定 |
|---|---|---|---|---|---|---|---|
| 整改前 | 60 | ✗ | ✗ | ✗ | ✗ | ✗ | **全部 BLOCK** |
| 整改后 | 60 | ✗ | ✗ | ✗ | ✗ | ✗ | **全部 BLOCK** |

样本首包特征：
- 整改前：`len=150`，前 16 字节 `1c8fa27d396112f3...`，平均 1 比特数 **4.047/字节**，可打印 **32.7%**，最长连续可打印 **3**。
- 整改后：`len=180`，平均 1 比特数 **4.194/字节**，可打印 **41.1%**，最长连续可打印 **6**。

**结论**：首 24 字节是随机 nonce，其余是 AEAD 密文，整体均匀随机 → popcount 落在 [3.4,4.6] 封锁区，可打印比例不足一半，没有可打印前缀，也没有 TLS/HTTP 魔数。**五条豁免规则一条都不满足 → GFW 会阻断**。

需要特别指出：我们上一轮做的抗指纹加固（随机 nonce、随机填充）让载荷**更接近均匀随机**，对 DPI 指纹有好处，但对 GFW 的"全加密检测"是**负优化**——它正是把均匀随机当作封锁信号。这两类对抗目标不同，不能混为一谈。

## 4. 解决方案（历史 TCP 方案；当前 UDP-only 无需实施）

CCS 2026 的核心方法论是：利用 **DPI 与真实端点之间的解析差异**。论文 §4.5 已证实的差异是"**GFW 只看第一个 TCP 数据包**"——只要让首包命中任一豁免规则，后续整条加密连接都会被放行。**但外部传输改为 UDP-only 后，这条差异不再有可利用的对象**：没有 TCP accept 路径，也没有"第一个 TCP 载荷"。下列方案保留作历史记录；若未来要针对 UDP 侧的检测器（如 QDPI `entropy_score`）做规避，需要重新设计，不能直接套用 TCP 前缀方案。

### 方案 A（历史推荐，现已不适用）：首包可打印前缀（命中 Ex2）

历史上是在 TCP 连接的第一个载荷前追加 **6 字节随机可打印 ASCII**，服务端在读握手帧前先消费掉这 6 字节：

- 对应论文 Ex2：前 6 字节全在 `[0x20,0x7e]` → 豁免。
- **必须随机生成这 6 字节**：若所有连接都用固定前缀，它本身就成了可被封锁的稳定签名（多态优于固定隐写）。
- 不改 AEAD、不改帧格式语义；只是首帧前的一段明文前缀。
- 对 UDP 无需应用（该检测系统不涉及 UDP）。
- **实现路径已不存在**：`driver.rs` 的 TCP `accept` / `read_exact(NONCE_AND_META_LEN)` 读取路径已随 TCP 外部传输一并移除。若真的要在 UDP 上做等价处理，需要在 UDP 握手/路由封装层增加前缀消费逻辑，并重新抓包验证；当前没有计划这么做，因为该系统本就不检测 UDP。

### 方案 B（已否决）：TLS 魔数前缀（命中 Ex5）

首包前 3 字节置为 `16 03 01`（TLS ClientHello 记录头），服务端剥离。**不要实施**：

- 它确实能过 USENIX'23 那一版 FET 的 Ex5（查前 3 字节），但这是**模仿（mimicry）策略**。Houmansadr 等人的结论是模仿式混淆有根本缺陷——无法无缝模拟目标协议的所有实现细节；USENIX Security 2024《Fingerprinting Obfuscated Proxy Traffic》也证实即便隧道进 cover 协议仍可凭实现差异被识别。GFW 早在 2012 年就用独特 TLS cipher suite 识别过 Tor。
- **两头不靠**：不是真 TLS（DPI 完整解析 ClientHello 即穿帮），又放弃了随机化优势。主动探测更致命：NDSS 2020《Detecting Probe-resistant Proxies》指出审查者发一个正常 ClientHello，真实 TLS 服务器回 Alert，而本服务端对不能解密的探测静默零响应——这个差异就是判据。
- 真要抗主动探测只有"完整 TLS 隧道 + decoy 反向代理"（HTTPT / Prisma 的做法：探测落到真实网站），但工作量大且违背本项目"不用 TLS、无需域名"的设计，不在 V0.2 范围。

若要利用解析器差异，正道是 CCS'26 归纳的那类（见 USENIX'25 QUIC 论文中 GFW 的解析怪癖：CRYPTO 帧长度写 0 仍按剩余负载推断、只认 QUIC v1 等），而不是假装成某个协议。方案 A 走的是 randomization 阵营（Ex2 可打印前缀），不伪装成任何具体协议，没有这个缺陷。

### 方案 C（历史纵深，现已不适用）：首包极短 + 延迟发送（利用 §4.5）

论文 §4.5 证实 GFW 只看首包且不重组：先发一个 1 字节可打印载荷（如 `X`，popcount 3 → 命中 Ex1），等待后再发真正的加密帧。这需要服务端支持"首包吞噬"（历史上属于 TCP 握手读取路径）。TCP 路径移除后该方案同样失去实施对象；UDP 隧道的 0-RTT 首 flight 本身已把 SOCKS5 请求与数据 piggyback 在一个数据报内，无法再插入独立的 TCP 首包。

### 方案 D（运维，P1）：IP 选择而非端口

- 论文 §6：GFW 只监控热门数据中心的特定 IP 段，且约 26% 概率阻断。优先选择未被广泛封锁的 IP 段/机房，比换端口有效得多。
- 换端口仅用于消除 nDPI 误报（见 `traffic-analysis.md` §3.3），**不要指望它过 GFW**。

### 方案 E（主动探测，P2）：保持零响应

当前对畸形/认证失败报文零响应字节的设计已经符合 probe-resistance。若未来在 UDP 握手上实现类似的前缀方案，需确保：对任意探测包（包括看起来像 TLS/HTTP 的探测）服务端行为一致——不泄漏"这是 ShadowLemon 服务端"。注意：静默零响应虽能防"重放探测"，但 NDSS 2020 指出审查者可用"连接何时/如何关闭（FIN vs RST）、是否回数据"来区分代理与正常服务器；这只是纵深防御，不能当成单点保障。UDP 没有 FIN/RST，这一区分维度在 UDP-only 传输下不再存在。

## 5. 实施优先级（历史）

1. 方案 A–C 针对的是已移除的 TCP 外部传输，**当前均无需实施**；USENIX'23 检测器不覆盖 UDP。
2. 方案 D（IP 选择而非端口）仍写入运维文档，纠正"换端口可过墙"的错误认知。
3. 方案 E（零响应、probe-resistance）继续保持。
4. 当前真正需要关注的是 UDP 数据报的高熵特征（QDPI `entropy_score`，见 `traffic-analysis.md`），而不是 TCP 首包豁免规则。

## 6. 自动搜索设施与实测筛选结果

已落地 `tools/gfw-search.rs`：把 OpenGFW 的 FET 分析器（`analyzer/tcp/fet.go`）逐行等价移植为纯 Rust 工具，无需 Docker/NFQueue/root 即可离线评估，并自动变异首包前缀、搜索稳健规避方案。用法见 `tools/gfw-search.md`。

- `check` 复核：整改前后各 60 条首包均 **60/60 BLOCK**，与前面的独立脚本结论一致。
- `search` 在 20 条真实首包 × 4 次随机采样（共 80 次）上要求**全部豁免**，结果：

| 策略 | 前缀长度 | 命中规则 | 稳健性 |
|---|---|---|---|
| 随机可打印前缀 | **6 字节** | Ex2 | 80/80 |
| TLS 魔数 `16 03 01` | 3 字节 | Ex5 | 80/80 |
| HTTP 方法（如 `PUT`） | 3 字节 | Ex5 | 80/80 |

低/高 popcount 前缀在采样长度内不能稳定把 ex1 推出 [3.4,4.6]，未列为稳健方案。搜索结果**印证了方案 A 是最短且无模仿缺陷的选择**；方案 B 同样有效但需承担深层 TLS 解析风险。

> 注意：以上判断基于 GFW 2021–2023 的公开测量与 2026 年规避研究，且自动搜索只验证历史 TCP 首包的 FET 豁免、未验证服务端前缀剥离。该 FET 系统不检测 UDP，当前 UDP-only 版本不在其判定范围内；这些搜索结果仅作历史记录，未实施、也不再需要实施到已删除的 TCP accept 路径。要评估 UDP 流量在真实网络中的表现，仍需在中国境内 VPS 上做 before/after 实测（参见 CCS 2026 的评估方法：受审查 VPS + 两端抓包 + 残留封锁判定），并重点关注 QDPI `entropy_score` 一类的高熵启发式。
